# Workout Tracker

Персональный трекер тренировок для iPhone и Desktop. Проект начинается как локальное веб-приложение (PWA), разрабатывается на одной машине и при готовности может быть развёрнут на Dockhost.

> **Цель MVP:** создавать и редактировать планы тренировок, выполнять их с записью фактических результатов и обмениваться структурированными данными с ChatGPT через JSON.

---

## 1. Принятые архитектурные решения

| Область | Решение |
|---|---|
| Клиент | React + TypeScript |
| Сборка и dev-сервер | Vite |
| Формат приложения | PWA |
| UI | Tailwind CSS + shadcn/ui, собственные компоненты |
| Backend | Node.js + Fastify |
| База данных | SQLite |
| Доступ к БД | Drizzle ORM |
| Миграции | Drizzle Kit |
| Валидация | Zod |
| Локальный режим разработки | Всё работает на компьютере разработчика |
| Будущий хостинг | Dockhost |
| AI-интеграция MVP | Импорт/экспорт JSON вручную через ChatGPT |
| Оффлайн в MVP | Кэширование оболочки PWA; операции с тренировками требуют доступного API |

### Почему такой стек

- **React + TypeScript** — зрелая экосистема, типизация и удобная разработка интерфейса для телефона и десктопа.
- **Vite** — быстрый dev-сервер и сборка.
- **PWA** — установка на главный экран без публикации в App Store.
- **Fastify** — компактный HTTP API между интерфейсом и базой данных.
- **SQLite** — простая файловая реляционная БД, подходящая персональному проекту.
- **Drizzle ORM** — типобезопасный TypeScript-слой для запросов к SQLite.
- **Drizzle Kit** — создание и применение миграций схемы БД.
- **Zod** — проверка входных данных API и импортируемых JSON.

### Почему пока без IndexedDB

В MVP используется одна серверная база SQLite. IndexedDB не добавляется, чтобы не создавать две копии данных и отдельную задачу синхронизации/разрешения конфликтов. PWA может кэшировать статические файлы интерфейса, но для чтения и записи тренировок нужен доступ к Fastify API.

Если позже понадобится полноценный оффлайн-режим, можно добавить IndexedDB как локальное хранилище и спроектировать синхронизацию отдельно.

## 2. Архитектура приложения

```text
┌──────────────────────────────────────────────┐
│                  Клиент                      │
│                                              │
│  React + TypeScript + Vite + PWA             │
│  Mobile-first UI / Desktop responsive UI    │
└──────────────────────┬───────────────────────┘
                       │ HTTP / JSON
                       ▼
┌──────────────────────────────────────────────┐
│                  Backend                     │
│                                              │
│  Node.js + Fastify                           │
│  API routes → services → repositories       │
│  Zod validation                              │
└──────────────────────┬───────────────────────┘
                       │ Drizzle ORM
                       ▼
┌──────────────────────────────────────────────┐
│                 Persistence                  │
│                                              │
│  SQLite database file                        │
│  Drizzle schema + migrations                  │
└──────────────────────────────────────────────┘
```

### Разделение ответственности

- **React-клиент** отвечает за отображение, навигацию, формы и состояние интерфейса.
- **Fastify API** — единственная точка доступа клиента к данным.
- **Сервисный слой** содержит правила предметной области: создание тренировок, запуск сессий, завершение и импорт.
- **Репозитории** инкапсулируют запросы Drizzle.
- **SQLite** хранит постоянные данные.

Не обращаться к SQLite напрямую из React. Не помещать SQL-запросы в UI-компоненты.

### Локальная разработка и доступ с iPhone

На этапе разработки frontend и backend запускаются на компьютере. Для тестирования на iPhone:

- телефон и компьютер могут находиться в одной Wi-Fi/LAN-сети;
- Vite и Fastify должны слушать доступный сетевой интерфейс (`0.0.0.0`), а не только `localhost`;
- API base URL должен задаваться конфигурацией окружения;
- CORS должен разрешать только нужные dev-origin;
- если для установки/проверки PWA на iPhone нужен HTTPS, можно временно использовать Cloudflare Tunnel или другой HTTPS-туннель.

Важно: `localhost` на iPhone означает сам iPhone, а не компьютер. Если backend работает на компьютере, телефон должен обращаться к его LAN-адресу или адресу туннеля. Компьютер и backend должны быть включены и доступны.

### Будущий деплой на Dockhost

При переносе на Dockhost:

1. Собрать frontend для production.
2. Раздавать production-статику через выбранную конфигурацию приложения или отдельный static hosting.
3. Развернуть Fastify API.
4. Хранить SQLite-файл на постоянном диске/volume, а не во временной файловой системе контейнера.
5. Настроить переменные окружения, URL API и HTTPS.
6. Настроить резервное копирование SQLite.

Не предполагать, что файловая система контейнера постоянная: до деплоя проверить, как Dockhost предоставляет persistent storage. SQLite-файл не размещать в синхронизируемой папке iCloud/Dropbox и не открывать одну БД одновременно нескольким независимым backend-процессам.

## 3. Основные функциональные блоки MVP

### Блок 1. Foundation

- Инициализировать React + TypeScript + Vite.
- Подключить PWA.
- Настроить Fastify backend.
- Подключить SQLite и Drizzle.
- Настроить Zod.
- Создать базовую навигацию и общие UI-компоненты.
- Настроить единый запуск frontend и backend в dev-режиме.
- Добавить health-check endpoint.

### Блок 2. Workout Builder

Пользователь может:

- создавать тренировку;
- редактировать и удалять тренировку;
- задавать название и описание;
- добавлять упражнения непосредственно внутрь конкретной тренировки;
- менять порядок упражнений;
- указывать целевые подходы, повторы, вес и отдых;
- добавлять заметки;
- при необходимости прикреплять изображение к тренировке или упражнению.

Отдельной глобальной библиотеки упражнений в MVP нет. Упражнения принадлежат конкретной тренировке.

### Блок 3. Workout Tracker

Пользователь может:

- запустить тренировку на основе шаблона;
- отмечать выполненные подходы;
- записывать фактические повторы и вес;
- записывать RPE;
- видеть и запускать таймер отдыха;
- добавлять комментарии;
- пропускать упражнение;
- завершать тренировочную сессию.

Фактическое выполнение сохраняется отдельно от шаблона. Изменение результата сессии не должно перезаписывать план тренировки.

Таймер должен вычислять оставшееся время по целевому timestamp, а не полагаться только на счётчик интервалов. На iOS нельзя обещать гарантированную работу фонового таймера, звука или вибрации при свёрнутом PWA.

### Блок 4. AI Exchange

Обмен данными с ChatGPT в MVP выполняется через JSON:

1. Пользователь экспортирует программу тренировок и, при необходимости, историю.
2. Отправляет JSON в ChatGPT.
3. ChatGPT предлагает изменения или создаёт новые тренировки в согласованном формате.
4. Пользователь вставляет JSON или загружает файл в приложение.
5. Приложение проверяет структуру и показывает preview.
6. Пользователь подтверждает импорт.

Импорт не должен автоматически и незаметно перезаписывать существующие данные.

## 4. Модель данных

Это минимальная предметная модель. Имена и поля можно уточнить при реализации, сохраняя разделение шаблона и факта.

### `workouts`

Шаблон тренировки:

- `id`
- `name`
- `description` (nullable)
- `createdAt`
- `updatedAt`

### `workout_exercises`

Упражнения, вложенные в конкретный шаблон:

- `id`
- `workoutId` — внешний ключ на `workouts`
- `name`
- `description` (nullable)
- `position` — порядок в тренировке
- `plannedSets`
- `plannedReps` (nullable)
- `plannedWeight` (nullable)
- `restSeconds` (nullable)
- `notes` (nullable)
- `imagePath` (nullable, если изображения реализуются в MVP)

Не создавать глобальную таблицу-каталог упражнений.

### `workout_sessions`

Факт выполнения тренировки:

- `id`
- `workoutId` — ссылка на исходный шаблон
- `workoutNameSnapshot` — название на момент запуска, чтобы история не зависела от будущего переименования шаблона
- `startedAt`
- `completedAt` (nullable)
- `status` — например `in_progress`, `completed`, `abandoned`
- `notes` (nullable)

### `set_logs`

Фактические подходы в рамках сессии:

- `id`
- `sessionId`
- `workoutExerciseId` — ссылка на упражнение шаблона
- `exerciseNameSnapshot` — название на момент выполнения
- `setNumber`
- `plannedReps` (nullable)
- `actualReps` (nullable)
- `plannedWeight` (nullable)
- `actualWeight` (nullable)
- `rpe` (nullable)
- `isCompleted`
- `completedAt` (nullable)
- `notes` (nullable)

При старте сессии нужно зафиксировать необходимые данные шаблона в сессии/логах, чтобы последующее редактирование тренировки не искажало историю. Для надёжности можно сохранять snapshot упражнений и их плановых параметров.

### Общие правила данных

- Использовать единый формат ID; предпочтительно UUID/строковые ID, чтобы в будущем упростить JSON-обмен и синхронизацию.
- Хранить даты в UTC (ISO 8601 или Unix timestamp), отображать в локальном часовом поясе устройства.
- Добавить внешние ключи и подходящие индексы.
- Удаление шаблона не должно случайно уничтожать историю завершённых сессий. Выбрать безопасную стратегию: запретить удаление при наличии истории или использовать архивирование/soft delete.
- Изображения хранить файлами в локальной папке uploads, а в БД — относительный безопасный путь. Не хранить большие изображения в виде base64 в SQLite.

## 5. API (ориентир для MVP)

Маршруты могут быть уточнены во время реализации, но придерживаться REST-подхода и не создавать лишние endpoints.

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/health` | Проверка доступности backend |
| `GET` | `/api/workouts` | Список тренировок |
| `POST` | `/api/workouts` | Создание тренировки |
| `GET` | `/api/workouts/:id` | Получение тренировки |
| `PATCH` | `/api/workouts/:id` | Изменение тренировки |
| `DELETE` | `/api/workouts/:id` | Удаление/архивирование тренировки |
| `POST` | `/api/workouts/:id/sessions` | Запуск сессии |
| `GET` | `/api/sessions` | История сессий |
| `GET` | `/api/sessions/:id` | Детали сессии |
| `PATCH` | `/api/sessions/:id` | Обновление фактических результатов |
| `POST` | `/api/sessions/:id/complete` | Завершение сессии |
| `GET` | `/api/export` | Экспорт данных |
| `POST` | `/api/import/preview` | Проверка и предварительный просмотр JSON |
| `POST` | `/api/import/commit` | Подтверждённый импорт |

Все входные payload должны проходить Zod-валидацию. Ошибки API должны иметь единый предсказуемый формат.

## 6. JSON Exchange: формат и безопасность

Начать с версионированного формата:

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-11-22T12:00:00.000Z",
  "workouts": [],
  "sessions": []
}
```

Правила:

- `schemaVersion` обязателен.
- Проверять весь JSON через Zod до записи в БД.
- Показывать пользователю preview: сколько тренировок/упражнений/сессий будет добавлено или изменено.
- По умолчанию импортировать как новые записи, не перезаписывая существующие.
- Если нужен режим замены, требовать явного выбора и подтверждения.
- Выполнять запись импорта транзакционно: либо весь импорт успешен, либо не записывается ничего.
- Не доверять ID из внешнего JSON без проверки; при конфликте генерировать новые ID и обновлять внутренние ссылки.
- Не исполнять содержимое JSON как код и не принимать произвольные пути к файлам.

ChatGPT в MVP не подключается к приложению напрямую и не получает автоматический доступ к SQLite. Пользователь вручную передаёт JSON между чатом и приложением.

## 7. UI/UX

### Принципы

- Mobile-first: основной сценарий — использование на iPhone.
- Responsive layout для десктопа.
- Тёмная тема как основной визуальный вариант; не усложнять MVP множеством тем.
- Крупные зоны нажатия и минимум действий во время тренировки.
- Быстрый ввод повторов и веса.
- Чёткое различие между плановыми значениями и фактическими результатами.
- Общие дизайн-токены и переиспользуемые компоненты.

### Основные экраны

1. **Home**
   - следующая/выбранная тренировка;
   - быстрый запуск;
   - последние завершённые занятия.

2. **Workouts**
   - список шаблонов;
   - создание и редактирование;
   - упражнения и их порядок.

3. **Active Workout**
   - текущая сессия;
   - карточки упражнений;
   - список подходов;
   - ввод фактических значений;
   - таймер отдыха;
   - завершение занятия.

4. **History**
   - минимальный список завершённых тренировок;
   - просмотр подробностей сессии.
   - без сложных графиков и аналитики в MVP.

5. **AI Exchange**
   - экспорт JSON;
   - импорт JSON через вставку текста или загрузку файла;
   - preview и подтверждение.

### Визуальные ориентиры

В качестве UX-референсов можно изучить Hevy и Strong: быстрый ввод подходов, понятные карточки упражнений и минимальное количество действий. Не копировать их интерфейс буквально.

## 8. PWA и оффлайн-ограничения

В MVP:

- настроить manifest и service worker;
- кэшировать оболочку приложения и статические ресурсы;
- показывать понятное сообщение, если API недоступен;
- не обещать полноценную оффлайн-работу с тренировочными данными;
- не добавлять IndexedDB и синхронизацию в этом этапе.

Будущее расширение:

- IndexedDB (например, через Dexie) как локальная база устройства;
- очередь локальных изменений;
- синхронизация с backend;
- стратегия разрешения конфликтов;
- индикатор статуса синхронизации.

Добавлять это только после появления реального требования к оффлайн-записи тренировок.

## 10. Что не входит в MVP

Не добавлять без отдельного согласования:

- нативное iOS-приложение;
- watchOS-приложение;
- HealthKit и импорт Apple Health;
- IndexedDB и полноценный offline-first;
- MCP-сервер;
- встроенный AI-чат или прямой вызов LLM API;
- глобальную библиотеку упражнений;
- сложную аналитику, графики и рекомендации;
- авторизацию, пользователей, социальные функции;
- облачную синхронизацию между несколькими устройствами;
- платёжную систему и подписки.

## 11. План реализации

Ориентироваться на последовательное выполнение блоков:

1. **Foundation** — структура проекта, React/Vite/PWA, Fastify, SQLite, Drizzle, Zod, базовая навигация.
2. **Workout Builder** — создание и редактирование тренировок и вложенных упражнений.
3. **Workout Tracker** — запуск сессии, логирование подходов, таймер отдыха, завершение.
4. **AI Exchange** — JSON export/import, валидация, preview и безопасное применение.
5. **Проверка и исправления** — мобильная адаптация, обработка ошибок, тесты критических сценариев.

Ориентировочная оценка первого прохода — 7–8 часов, если не расширять объём и использовать coding agent. Это оценка для простого рабочего прототипа, а не гарантия законченного production-продукта.

### Критерии готовности MVP

- Можно создать, изменить и удалить/архивировать шаблон тренировки.
- Можно добавить упражнения и задать плановые подходы, повторы, вес и отдых.
- Можно начать сессию и записать фактические результаты.
- Редактирование шаблона не меняет завершённую историю.
- Можно посмотреть список и детали прошлых сессий.
- Можно экспортировать JSON и импортировать его после preview и подтверждения.
- Данные сохраняются после перезапуска backend.
- Интерфейс работает на iPhone и десктопе при доступном backend.
- Production-сборка проходит без ошибок.

## 12. Правила разработки

- Сначала прочитать весь README и согласовать план реализации с пользователем.
- Делать блоки по порядку, не перескакивать к будущим функциям.
- Не расширять scope без явного запроса.
- После каждого блока запускать lint/typecheck/tests/build (те команды, которые настроены в проекте).
- Не оставлять фиктивные данные в production-сценариях.
- Все изменения схемы БД проводить миграциями.
- Не хранить секреты в репозитории; использовать `.env` и `.env.example`.
- Добавить SQLite-файл, пользовательские изображения и секреты в `.gitignore`.
- Проверять ввод на сервере через Zod, даже если он уже проверен на клиенте.
- Не связывать UI напрямую с Drizzle или SQLite.
- Сохранять разделение между шаблонами тренировок и фактическими сессиями.
- Если решение требует выбора, предпочитать простое и обратимое; спорные расширения сначала согласовывать.
