# app-foundation Specification

## Purpose
Базовый каркас приложения: доступность и предсказуемое поведение API, сохранность данных, PWA-оболочка и навигация, на которые опираются все остальные возможности.
## Requirements
### Requirement: Health-check endpoint
Backend SHALL отвечать на `GET /api/health` статусом 200 и JSON `{ "status": "ok", "time": "<ISO 8601 UTC>" }`, проверяя доступность БД.

#### Scenario: Backend доступен
- **WHEN** клиент вызывает `GET /api/health`
- **THEN** ответ имеет статус 200, `status` равен `"ok"`, `time` — корректная ISO-строка в UTC

### Requirement: Единый формат ошибок API
Все ошибки API MUST возвращаться в формате `{ "error": { "code": string, "message": string, "details"?: unknown } }` с соответствующим HTTP-статусом. Ошибки валидации MUST иметь код `VALIDATION_ERROR` и статус 400, неизвестный маршрут — `NOT_FOUND` и 404, непредвиденные ошибки — `INTERNAL_ERROR` и 500 без утечки stack trace.

#### Scenario: Неизвестный маршрут
- **WHEN** клиент вызывает `GET /api/does-not-exist`
- **THEN** ответ имеет статус 404 и тело `{ "error": { "code": "NOT_FOUND", ... } }`

#### Scenario: Невалидный payload
- **WHEN** клиент отправляет тело, не проходящее Zod-схему маршрута
- **THEN** ответ имеет статус 400, `error.code` равен `VALIDATION_ERROR`, а `error.details` перечисляет проблемные поля

#### Scenario: Внутренняя ошибка
- **WHEN** обработчик маршрута выбрасывает непредвиденное исключение
- **THEN** ответ имеет статус 500, `error.code` равен `INTERNAL_ERROR`, тело не содержит stack trace

### Requirement: Серверная валидация входа
Каждый маршрут, принимающий body, params или query, MUST валидировать их Zod-схемой на сервере независимо от клиентской проверки.

#### Scenario: Валидация на сервере
- **WHEN** запрос в обход UI содержит поле неверного типа
- **THEN** запрос отклоняется с `VALIDATION_ERROR`, данные в БД не меняются

### Requirement: Сохранность данных
Данные SHALL храниться в SQLite-файле, путь к которому задаётся переменной окружения (по умолчанию `data/workout-tracker.db`), и MUST сохраняться после перезапуска backend. Схема БД MUST создаваться и изменяться только миграциями, применяемыми при старте или отдельной командой.

#### Scenario: Перезапуск backend
- **WHEN** данные записаны, backend остановлен и запущен снова
- **THEN** ранее записанные данные доступны

#### Scenario: Пустая БД
- **WHEN** backend стартует, а файла БД нет
- **THEN** файл создаётся и все миграции применяются автоматически

### Requirement: Конфигурация через окружение
API base URL клиента, порт и host backend, путь к БД и разрешённые CORS-origin SHALL задаваться переменными окружения; в репозитории MUST быть `.env.example`, а `.env`, файлы БД и `uploads/` MUST быть в `.gitignore`.

#### Scenario: Запрос с неразрешённого origin
- **WHEN** браузер с origin, отсутствующим в списке разрешённых, делает запрос к API
- **THEN** ответ не содержит заголовков, разрешающих этот origin

### Requirement: PWA-оболочка
Приложение SHALL иметь web manifest (имя, иконки, `display: standalone`, тёмный theme color) и service worker, кэширующий оболочку и статические ресурсы. Данные тренировок MUST NOT кэшироваться для оффлайн-записи.

#### Scenario: Production-сборка
- **WHEN** выполняется production-сборка frontend
- **THEN** в результате присутствуют manifest и service worker, сборка завершается без ошибок

### Requirement: Навигация по основным экранам
Интерфейс SHALL предоставлять навигацию между экранами «Главная», «Тренировки», «История», «AI-обмен» (нижняя панель на мобильных, боковая или верхняя на десктопе), использовать тёмную тему по умолчанию и русский язык интерфейса. Экран активной тренировки доступен по отдельному маршруту.

#### Scenario: Переход между экранами
- **WHEN** пользователь нажимает пункт навигации
- **THEN** открывается соответствующий экран без перезагрузки страницы

### Requirement: Сообщение о недоступном API
Если API недоступен, интерфейс MUST показывать понятное сообщение о недоступности сервера вместо пустого экрана или бесконечной загрузки, и давать возможность повторить запрос.

#### Scenario: Backend остановлен
- **WHEN** пользователь открывает экран, а backend не отвечает
- **THEN** отображается сообщение «Сервер недоступен» с кнопкой повтора
